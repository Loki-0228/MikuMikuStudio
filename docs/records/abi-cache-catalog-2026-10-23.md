# 缓存索引快照发布

本批实现内部 `cache_catalog`，在不可变快照之外增加独立提交记录。它提供完整字节快照的读取、初始化与跨进程比较交换，供后续业务索引使用。快照内容目前仍是不透明字节，工程关联、固定状态、维护代次、条目预算、回收和消费者尚未接入，不能将本批视为完整缓存管理器。

## 发布规则

专用元数据目录只接受 `.lock`、`snapshots` 和 `commits`。初始化要求两个子目录均没有条目；已存在快照却没有提交记录时返回 `RecoveryRequired`，不生成新身份掩盖残留数据。未知名称、损坏或未来格式同样不能视为空库。读取不存在的目录返回 `Missing`，不会初始化存储身份；存在目录的读取可以创建正常锁文件。

首次提交生成存储身份并写入 revision 1，后续提交必须提供读取所得的原快照。宿主取得根目录文件锁后重新读取全部提交链，比较原存储身份、revision 和完整提交文件身份；旧快照或其他目录的快照返回 `Conflict`。同值提交仍生成下一 revision，输入字节、预期快照和输出可以引用同一个快照对象。

发布先创建并刷新完整数据快照，再取得该快照的读租约，最后创建并刷新提交记录。提交记录引用新快照及前一提交的完整文件身份。不存在可供读者使用的半份索引，也不依赖文件重命名。历史元数据租约保持到本次操作结束，新快照租约保持到发布结束。

所有错误都保留调用方原输出。尝试写入提交记录之后发生错误返回 `Indeterminate`，表示调用方必须重新读取。它不保证此次更新未发生，也不是可以盲目重试的错误。当前没有独立 operation ID 或自动重试协议；如果之后又发生其他提交，仅靠读取最新快照不能证明某次尝试是否曾经成功。

## 中断与损坏

完整、未被提交引用的数据快照继续保留，并计入元数据上限。已存在健康提交链时，这种快照不会成为当前版本。半写快照、半写提交、断链、分叉、文件身份变化及被引用快照缺失均返回 `RecoveryRequired`，不会自动选择旧版本冒充最新状态。

这部分提供故障检测和明确结果，尚未提供所有中断状态的自动修复。需要额外的身份核对和回滚协议后，才能安全清理不完整文件。禁止通过忽略坏记录、按时间戳选择旧记录或重新初始化目录消除错误。

## 格式与边界

提交记录的负载固定为 368 字节，使用 `MMSCacheHead0001` 标记、显式小端字段和全零保留区域。记录包含 revision、存储身份、新快照引用及前一提交引用。引用保存代次文件名、种类、所有者、逻辑键、摘要、长度、卷序列号和文件索引；不直接保存 C++ 对象布局。初始提交的前一引用必须全部为零。

| 限制 | 当前值 |
| --- | --- |
| 单个快照负载 | 16 MiB |
| 提交记录数量 | 64 |
| 数据快照数量，含未引用快照 | 128 |
| 元数据总长度，含文件头 | 64 MiB |

达到上限返回 `Limit`，不会删除历史或继续发布。这些是当前内部发布层的硬限制，不是用户设置中的缓存容量上限。历史压缩和业务索引 schema 仍待实现，因此该模块尚未用于生产缓存命中、Touch 或工程关联。

`cache_files::Directory::Child` 使用父目录已固定的卷 GUID 路径打开一个经过校验的子目录，避免持有根锁后重新解析原盘符。子目录及其派生租约保留祖先保护句柄。`EnumerateAll` 供元数据目录检查全部条目，原来的候选文件枚举接口保持原有用途。

四个受控错误实现分别绕过旧版本比较、忽略根目录未知文件、忽略未来提交记录和放开第 65 次提交，均由指定断言检出。`negatives.json` 记录替换及恢复散列；生产源码按原字节恢复并重建后，基础专项再次通过。审查还修正了测试自身的一处判据：其他目录的预期快照先返回 `Conflict`，不能要求它进入损坏目录的恢复检查，也不能因此放宽生产 CAS。

分配专项观察到 11 次 `RecoveryRequired` 和 8 次 `Indeterminate`。这些失败保留了现场与原输出，不代表自动恢复已实现。注入范围是健康调用路径中的当前线程普通 `new/new[]`，不涵盖失败路径新增分配、多处同时失败、对齐分配、CRT `malloc`、Win32 或 CNG 系统分配。

原始配置容量专项首次失败时，D 盘只剩 2,232,320 字节。失败日志及快照原始字节已保留。Codex 将本批自建的大文件夹具压缩，逐文件比较 SHA-256 并检查归档 CRC 后才释放对应测试副本；没有清理用户文件。测试增加了 80 MiB 可用空间前置检查和提交返回值诊断，并修正 SHA-256 测试辅助对象在构造失败时的资源释放。恢复空间后，两配置最终容量专项均通过。`budget-archive-manifest.json` 保存原文件长度、摘要和归档位置，归档用于检查原始字节，不承诺解压后恢复原卷文件身份。

## 下一实施单元

在接入消费者前，先实现有界历史维护和有来源的中断恢复。初始化已使用一次提交，当前只允许再提交 63 次；不能通过提高常数、删除旧链或重新初始化身份来替代维护协议。检查点必须保存当前状态和全局版本，在持久化后才允许按精确身份退休旧文件；未识别文件和未获授权的损坏记录继续拒绝。维护本身也需要预留记录数及字节空间。

业务索引随后承担条目 schema、跨进程容量预留、工程历史关联、固定、租约、清理和失效代次。自动回收、手动可回收清理、指定工程及全部清理须保留 main 各自的固定与共享规则。效果消费者、普通纹理、ABI 事务纹理和管理窗口分别接入真实后端。具体依赖与验收矩阵保存在本批 `business-next.txt`，这些项目仍未实现。
