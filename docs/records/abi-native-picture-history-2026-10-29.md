# 原生背景图片共同历史

2026-10-29，ABI 工作树已将图片导入、替换、显隐和移除接入共同历史。**19 组背景专项全部通过；全量原生历史后续因实际鼠标环境前提未满足而停止，尚不能宣布全量通过。** 本批更新前一份[准备与激活记录](abi-background-picture-activation-2026-10-29.md)中的菜单接线待办，不表示背景摆放历史已经完成。

## 已实现范围

内部 `NativePicturePlan` 提供 `Begin`、`Read`、`Clear`、`Visibility`、`Take`，由共同历史准备、提交及重放。长期记录保存不可变图片资产与呈现状态；每次准备再检查实时身份、设备和宿主字段。首轮已解码的候选直接用于提交，失败不先替换旧图，也不先改变历史游标。

最终补修将 `Begin` 改为原子、只读的 `QueryPictureSnapshot`，同时捕获票据、资产和图片修改代次，不为了准备操作激活空槽。空图上的取消、坏图和缺图保持票据为零；空槽再次 `Invalidate` 也会使旧计划失效。真实 `ResetAppState` 保留资产但撤回票据后，取消仍不激活图片，后续可直接显隐，不需要先导入或手动获取票据。

| 入口或操作 | 共同历史语义 |
| --- | --- |
| 菜单 232 导入、连续替换 | `ExplicitCommit`；两种模式都记录一次完整操作 |
| 图片拖放 | 接入同一 `TryLoadBoundPicture`；本批没有单独运行真实拖放消息验收 |
| 新菜单 32816 移除背景图片 | `ExplicitCommit`；清除纹理、资产、路径、尺寸及呈现状态，可撤销 |
| 菜单 233 显隐 | `Adjustment`；`AllOperations` 记录，`ExplicitOnly` 只应用显隐并保留既有重做分支 |

上述共同历史行为针对已有历史绑定的完整配置；未绑定时保留原生后备路径，原始兼容配置不因本批开放插件 ABI。新增的是内部宿主实现，没有新增公共 C ABI 服务，也没有改变 VMD／PMM 的保存格式。

显隐只拥有 enabled 字段，复用当前纹理，不重新解码。撤销显隐保留当前摆放，不把未记录的拖动一起撤销。图片替换或移除真正提交时，将离开图片的实时摆放、显隐保存到对应记录一侧；因此未登记的位置调整不会使后续图片撤销报过期，多轮往返也能保留各自呈现状态。

重放使用资产保留的编码字节与原解码配方，删除原文件后仍可撤销、重做。资源不足、解码失败、取消或无变化不部分提交，不丢失既有重做分支。图片记录的影响范围为工程数据和视口，不要求重置模型物理，也不移动播放头。

## 预算、刷新与释放

导入、替换和重放按共同历史限额检查准备阶段的保守资源量，包含当前与候选纹理及保留来源。来源字节预算仍是独立机制，不把历史限额等同于进程内存或驱动峰值上限。

`ExplicitOnly` 的显隐没有新增来源或 GPU 纹理，即使历史限额降到 16 MiB、低于现有纹理的保守估计，仍可复用资源隐藏／显示并保持撤销、重做栈。`AllOperations` 需要保留显隐记录，仍受记录预算约束。专项使用的 512 MiB 历史限额只是测试配置，并非本批修改用户默认值。

提交与 UI 刷新分开：菜单、移除按钮状态、背景顶点或视口刷新失败时，保留 `PendingPictureUiTicket`，后续安全点重试，不把已经成功的导入报成失败，也不追加第二条历史。图片 mutation 暂时阻止查询时保留同一待刷新票据；确认票据已被替换才丢弃过时请求。恢复条件后刷新一次，清除待办。

未绑定共同历史的移除也保留失败的刷新请求，通过实际 `WM_INITMENUPOPUP` 菜单安全边界重试。专项暂时摘下菜单使第一次刷新失败，再恢复菜单并发送真实菜单打开消息，验证显隐／移除状态恢复且待办清零。

被替换纹理在交换完成后才释放，释放位于注册表锁外，并受 UI 输入门禁保护；提交后的控件通知也处于门禁内。`ClearLegacyPicture` 的直接 `Release` 同样加上门禁。真实纹理的 IUnknown 私有数据观察器验证了替换、删除时的最终释放发生于 `bake::UiLocked()` 为真期间。这只证明销毁时的门禁状态，未发送动态 `WM_CLOSE`，不等于实际关闭重入的完整验收。

主要实现为 `src/plugins/native_picture_history.hpp/.cpp`、`src/media/background_picture_activation.cpp`、`src/window/picture_menu.cpp` 及菜单、拖放和共同历史刷新接线。专项为 `tests/native_picture_history_checks.inc`，通过完整隐藏宿主 `sidebar_resize_tests --picture-history-only` 运行。

新增图片共同历史专项覆盖：

- 两种历史模式、真实菜单 232／233／32816、连续导入／替换／移除、删源后的三轮撤销重做，以及保留来源的实际像素解码。
- 显隐复用纹理、显隐撤销保留当前摆放、`ExplicitOnly` 显隐保留重做、16 MiB 限额下两种模式的不同准入规则。
- 缺图、坏图、文件选择取消、无变化和限额不足，均保持当前图片与应保留的历史；菜单 215 网格操作与图片记录按同一时间顺序撤销、重做。
- 暂时移除真实顶点缓冲后导入仍成功且只有一条历史；刷新失败及 mutation 期间保留待办，恢复后菜单和六个顶点正确，重复刷新不再次提交。
- 空槽准备不激活、空槽再次失效拒绝旧计划、实际工程重置保留资产后的取消／直接显隐，以及未绑定移除在真实菜单打开边界重试刷新。
- 替换、移除时真实旧纹理的销毁门禁。几何检查暂用同尺寸、同格式的可读 D3D 缓冲，结束后恢复原资源；它验证生产写入的顶点，不宣称读取生产 WRITEONLY 缓冲或完成人工视觉验收。

全量原生历史回归中，原先 `MorphResetObjectChronology` 的 `PrepareInsertion` 失败已定位为夹具缺少附件 KeyPool；`tests/native_pose_scope_checks.inc` 已补齐有效池及清理，严格断言保持不变。之后 `NativeModelPhysicsUiChecks` 的计数失败已确认为测试混计预览退休请求和成功历史发布请求；现分别严格计数，仍要求只有一次合并后的 wake，全集已越过该点。此前 physics-ui-diagnosis-nc405016（本地证据，未随本文发布） 保留为旧失败证据。

扩大回归曾在场景身份恢复的 8,192 次分配故障扫描中未到达成功；同一程序独立身份专项通过 9,082 项，暴露了 `SceneIdentity::Replace` 随进程历史 ID 累积而重复全拷贝的生产性能问题。修复后只准备新增 ID 节点、预检容量后合并，保留失败原子性和全部防复用旧 ID，原扫描上限不变。最终验证（本地证据，未随本文发布）中两配置 ABI 契约各 45,133 项通过，新增大历史 ID 测试已越过，实际恢复扫描在 `successLimit=80` 成功。

全集随后运行到 `NativeCameraHudHistoryChecks`，因 `SetCursorPos` 返回 0、真实桌面鼠标未移动而停止，没有最终 PASS。这是鼠标夹具环境前提未满足，不能视为已完成鼠标验收，也不能据此认定产品代码失败；已向用户请求实际桌面运行 `--camera-hud-only`。详见[身份恢复修复记录](abi-scene-identity-restore-2026-10-29.md)。本记录仍不将全量原生历史或全部 ABI 需求标为通过。

之后附件父级、附件 HUD 核心及同模型跟随的三项独立补验通过，ABI 开发程序也已构建且可选启动导入检查为空；具体证据及限制见上述身份恢复记录，没有覆盖 main 或稳定版程序。

## 仍未完成

背景图片摆放／拖动共同历史已在[后续批次](abi-picture-gesture-history-2026-10-29.md)实现并通过专项；视频资源 owner 与可恢复重放、总体资源预算、完整设备丢失与重建仍待推进。真实 DLL 插件记录与图片的交错、真实文件拖放消息及动态关闭重入没有由本专项验收；本批只验证与原生网格命令的交错。

Win7 SP1 x64、CPU 基础路径及 AMD 兼容要求不变，真机兼容和可见 UI／物理输入验收仍待完成。用户返回 `user32 main hwnd=000000000001000C` 只证明该烟雾程序能够创建窗口，不能替代这些验收。

目标范围不变，已只读核对 MMS main 最新提交仍为 `6facf91`；阴影相关同步继续暂缓。
