# 模型排序共同历史与容量边界

日期：2026-10-20。分支：`codex/plugin-abi`。继续处理[模型名称与选择错配](abi-model-order-2026-10-20.md)。

## 排序事务

模型绘制顺序与计算顺序在共同历史绑定下分别进入同一撤销队列。一次确定形成一次显式提交，两种历史模式相同；取消或未改变顺序不会删除已有 redo。普通未绑定路径与 `mmd932` 保留原生操作方式，普通插件 `mms.edit` 仍未开放。

对话框打开前捕获稳定模型身份、保留对象及两种顺序。编辑过程只改临时排列，确定后先校验完整排列，关闭对话框并释放临时数组，再准备和发布历史条目。初次发布检查两个来源字段和实例代次；撤销／重做只恢复该条目负责的顺序，保留当前选择、父模型引用、播放头及未登记姿态。

内存预算包含历史记录、排列及保留模型的实际资源记账。准备阶段失败不修改顺序；最终发布不分配内存。来源对象失效、其他草稿占用队列、内存预算不足或异常输入均拒绝提交。单字节索引转换之前先验证范围，`INT32_MIN` 等异常值不会先发生减法溢出。

发布成功后若原生列表刷新失败，保留已完成的事务并安排 UI 重试，不能回写旧顺序或重复增加历史。相同模型数量下的绘制顺序变化也会刷新列表映射。提交前同时检查既有附件列表排列，避免无效附件顺序使新模型排序提交后永久卡在 UI 重试门中。

## 第 255 项

模型有 255 个槽位，正常绘制和计算顺序为 1..255；部分旧场景使用顺序 0。原先若干遍历只访问 0..254，因此正常末项 255 会被遗漏。

本批将模型槽位容量与顺序值域分开：绘制查找表有 255 个来源槽和 256 个顺序位置，保留旧顺序 0。模型绘制、物理两阶段、物理烘焙、播放追帧、图片首帧以及 PMM 加载后的三个选择器均包含顺序 255。渲染仍按原规则保留重复顺序的首个槽位；物理仍执行所有匹配槽位。附件继续使用原有 0..254 顺序，不套用模型的一基规则。

可选 DX12 的对应遍历也同步修正，但本机 Win7 基础配置关闭 DX12，该分支未作运行验收。

## 255 上限与后续扩容

本批修复合法容量末项，不扩大模型数量上限。上限来自固定槽位、单字节顺序字段以及现有 PMM 的单字节模型数量，和显卡厂商无关。

用户确认继续使用 MMS 已有的非标准 PMM 扩展路线，不需要为扩容另起工程格式。现有保存代码已区分 `Polygon Movie maker 0002`／`0003`，并支持 `MMSXPMM2` 扩展尾段；但两种头部目前仍共用单字节模型计数、槽号和固定容量对象，所以“能保存扩展 PMM”尚不等于“已能保存超过 255 个模型”。

后续若扩大容量，应将 MMS 内部对象存储改为动态集合，稳定对象 ID 与显示／计算顺序分离，并迁移所有父子引用、求值、编辑及历史路径。扩展 PMM 以明确版本承载较宽的数量、对象 ID、排序及引用映射；加载器在分派格式时先识别新版本，再按对应布局读取，不能只改现有头部名称后直接加宽字段。旧 MMS 对不支持的版本应明确拒绝，不能误读或静默加载残缺工程。

255 应成为“导出兼容 MMD 的标准 PMM”时的限制，而不是 MMS 扩展工程的长期上限。标准导出超限时提示并允许选择范围；依赖模型或父子引用无法表达时同时说明转换或丢失内容，不能静默截断。标准 PMM／VMD 的既有兼容指标保持不变。此项是后续设计方向，本批未实现扩容或新版本编解码。
