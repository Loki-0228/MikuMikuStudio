# 绑定观察与已尝试工作的恢复

本批修复原属性范围刷新的一处重复消费：真实绑定变化已经记录工作，但来源观察和原请求连续发生内存失败后，普通补观察又把同一变化计为新工作。公共 C ABI、SELF 1.0、原队列和绑定身份均保持不变。接口语义见[原属性范围刷新](../../sdk/mms/scoped-property-refresh.md)。

## 失败与恢复规则

每个范围订阅在内部记录已尝试绑定工作的代次。原队列 `Take` 才消耗该次机会，普通观察只安装完整来源监听。已尝试的请求失败后，补观察保留原结果以及 CONSUMER、CAPACITY、DISPLAY_CAPACITY、HOST_WAKE 等待状态，只校正实际目标、图和缺失来源信息。

新的真实工作仍可执行。后续属性通知推进通知序号和工作代次；真实队列、显示或资源容量释放则可以恢复原工作，不额外递增这两项。容量重试沿用原时钟匹配条件，不使用定时器、递归刷新或普通观察制造机会。已接受票据或正在捕获的请求继续独占自己的调度决定。

来源发布保持原 SOURCE、CONSUMER 恢复条件。没有容量变化的纯发布不被当作属性 Notify。结构事件的既有待观察状态和单次请求规则保留，见[结构观察失败恢复](abi-scoped-observation-2026-10-22.md)。

## 真实反例

证据位于 `build/verification/abi-binding-observation-20261022/`，失败候选和日志均保留。

`candidate-02` 的完整与原始兼容配置分别运行 `red-binding-full-02`、`red-binding-original-02`，均在第 108 项失败。两份日志先确认以下前置条件：

- 原生 INPUT 已完成第一代工作，来源首次发布发生在绑定之前，未触发订阅。
- Bind 成功，其后置观察精确命中一次 112 字节分配故障，工作代次增至 2。
- 下一次 Drain 精确命中三次 112 字节故障，最后一次位于原 `CaptureProperty` 的来源预留分配。故障余额归零，原请求返回 MEMORY，等待 DISPLAY_CAPACITY，无消费或真实容量变化。
- 撤销故障注入后的第一次普通 Drain 却把工作增至 3 并完成。读取、准备和布局各多执行一次，原 MEMORY 停泊消失。

较早 `red-binding-full-01` 的诊断不足以区分状态比较发生在哪个阶段；本批用明确阶段、状态字段、来源版本及故障命中数重新定位，没有把该旧日志单独当作生产缺陷证据。

新增两个用例保留全部强断言。第一个要求六轮普通 Drain 保持失败状态和全部消费计数，再用真实属性 Notify 恢复。第二个在补观察前替换原来源快照，明确检查真实容量时钟推进，要求恢复同一序号和工作代次。后者不能单独证明尚未安装的来源监听收到了发布，因为真实快照释放本身已足够触发恢复。
