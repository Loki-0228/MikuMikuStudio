# 缓存索引检查点与退休回收

本批为内部 `cache_catalog::Store` 增加 `Checkpoint` 和 `CollectRetired`。检查点保留当前快照及全局 revision，并记录允许回收的旧文件身份。显式回收完成后，存储可以继续提交，不再受累计一生最多 64 条记录的限制。

快照负载仍是不透明字节。本批没有接入业务缓存、工程关联、固定状态、用户容量策略、效果或纹理消费者，也没有增加自动维护调度。前一批发布合同见[缓存索引快照发布](abi-cache-catalog-2026-10-23.md)。其中关于维护尚未实现的描述由本记录补充，其他发布与故障边界继续适用。

## 接口合同

接口声明位于 [cache_catalog.hpp](../../include/mikumikustudio/cache_catalog.hpp)，实现位于 [cache_catalog.cpp](../../src/io/cache_catalog.cpp)。

| 接口 | 当前行为 |
| --- | --- |
| `Checkpoint(expected, output)` | 在根目录文件锁内核对完整预期身份，发布同一负载的下一 revision。复用原快照文件，不复制负载，不删除旧文件。 |
| `CollectRetired(report)` | 重新读取并校验当前检查点，只尝试删除其名单中仍存在且身份相符的退休文件。返回分项报告。 |
| `Read(output)` | 校验检查点、退休文件和剩余活跃提交链。不会隐式回收。 |
| `Commit(expected, bytes, output)` | 继续使用原普通发布预算。前驱现在可以是检查点，仍不会隐式维护。 |

`Checkpoint` 比较预期快照的目录、存储身份、revision 和完整提交文件身份。旧预期或其他目录的预期返回 `Conflict`。预期与输出可以是同一个对象；所有失败保留原输出。成功后 revision 增加 1，存储身份及负载保持不变。达到 `UINT64_MAX` 返回 `Limit`。

检查点名单来自锁内已验证、实际存在的元数据文件。名单包含全部旧提交和旧检查点，以及当前快照以外的数据快照。上一轮尚未回收的文件继续纳入新名单；已经消失的条目不会重复积累。宿主持有元数据读租约直到操作结束，当前负载在发布期间也受到保护。

开始尝试写入检查点文件之后发生错误，接口返回 `Indeterminate`。这不能证明发布未发生。重新读取可能得到完整旧版本、完整新检查点，或 `RecoveryRequired`。当前没有 operation ID，不能据此自动重放原操作或承诺一次且仅一次提交。

## 检查点选择与来源校验

元数据目录仍只接受 `.lock`、`snapshots` 和 `commits`。所有实际存在的记录和快照都经过文件封装、摘要、格式与身份校验；已退休文件也不能因即将删除而跳过校验。未知名称、未来版本、损坏记录、断链和身份变化继续拒绝读取或回收。

存在多个检查点时，当前检查点必须按完整文件身份退休其余仍存在的检查点。两个未互相退休的检查点、同 revision 分叉或名单之外的孤立记录均返回 `RecoveryRequired`，不能只选择最大 revision。未退休的普通提交必须从当前检查点开始形成唯一连续链，每条记录的前驱身份都与实际前一记录一致。

当检查点的精确前驱文件仍存在时，检查点 revision 必须等于前驱 revision 加 1，快照引用也必须完全相同。已获授权退休的前驱消失后，检查点可以独立作为起点。读取旧的已退休检查点只校验其自身内容及身份，不再要求它引用的更老退休文件全部存在。

活跃链引用的每个快照都必须存在、完整且未列入退休名单。保护范围包含检查点及后续普通提交引用的快照，不只保护最后一条记录的负载。

## 格式与预算

[cache_catalog_codec.hpp](../../src/io/cache_catalog_codec.hpp) 定义检查点格式。新记录使用 `CatalogCheckpoint = 5`、`CheckpointKey = {3}` 和 `MMSCacheBase0001` 标记。编码为显式小端字段，不保存 C++ 对象布局。普通记录继续使用 `MMSCacheHead0001`，其前驱引用新增对检查点的支持。没有增加旧 MDS 标记的读取兼容。

检查点前 368 字节保存版本、revision、存储身份、当前快照和前驱引用。偏移 368 保存退休条目数量，偏移 372 的四字节保留字段必须为零；偏移 376 开始保存每条 160 字节的完整文件引用。退休名单按提交目录中的文件名排序，再按快照目录中的文件名排序。重复、乱序、缺失精确前驱、包含当前快照、未知类型和不匹配长度均被拒绝。

| 限制 | 当前值及适用范围 |
| --- | --- |
| 单个快照负载 | 16 MiB。检查点不增加一份快照。 |
| 普通提交记录数 | 发布后实际存在的普通提交及检查点合计不超过 64。退休但尚未消失的记录仍计数。 |
| 检查点记录预留 | 检查点可使用第 65 个位置。占用预留时，活跃链末尾必须是经过验证的检查点。 |
| 快照文件数 | 128，包含未引用快照和仍存在的退休快照。 |
| 普通元数据预算 | 64 MiB，包含全部实际存在元数据文件的 128 字节封装头。 |
| 检查点字节预留 | 32 KiB，仅检查点发布可使用。普通提交不能借用。 |
| 退休名单 | 最多 192 项。检查点负载最多 31,096 字节，加封装头为 31,224 字节。 |

检查点发布前，现有记录数和字节占用必须仍在普通预算内。预留已经被占用时，下一次检查点不能再次透支。只有文件实际从目录消失后，后续盘点才减少占用；标记为退休不减少计费。

读取和回收允许经过验证的检查点处于维护预留范围。存在检查点时，若当前活跃头是普通提交，却占用了第 65 个位置或超过普通字节预算，读取返回 `RecoveryRequired`。没有检查点的普通库仍按原上限返回 `Limit`，超过维护总上限也返回 `Limit`。

## 回收与报告

`CollectRetired` 在第一次删除前完成根锁、完整读取、授权名单和候选数组的准备。准备失败保留调用方原报告，不删除文件。开始回收后，宿主只释放自己对当前待删退休文件的租约，并保留活跃元数据的保护。删除调用 `cache_files::Directory::Remove`，再次通过同一个独占句柄核对完整身份和内容。

开始回收后的 `Ok` 表示报告已返回，不表示所有候选都已消失。部分删除不能回滚；后续调用可以继续收集名单中尚存在的文件。

| 报告字段 | 含义 |
| --- | --- |
| `attempted` | 本次读取确认仍存在、实际尝试删除的退休文件数。已经缺失的名单条目不计入。 |
| `absent` | `Remove` 返回 `DeletePending` 或 `Missing` 后，再次按同名检查确认 `Missing` 的数量。 |
| `busy` | `Remove` 返回 `Busy` 的数量，文件仍可能受到外部租约保护。 |
| `pending` | 删除返回 `DeletePending` 或 `Missing`，但再次检查未确认 `Missing` 的数量。包括复查出现 I/O 或分配错误，不仅是系统延迟删除。 |
| `failed` | 其他删除失败的数量。 |
| `absentBytes` | 本次确认目录项消失的文件长度之和，包含文件封装头。 |

`attempted` 等于 `absent + busy + pending + failed`。`absentBytes` 只描述命名空间中的文件消失，不能解释为文件系统已释放相同大小的物理磁盘空间。`DeletePending` 本身也不等于已经回收。

## 中断与未实现范围

完整检查点持久化后，部分退休文件的缺失属于授权状态。回收中断后重新读取仍可使用当前检查点，再收集剩余文件。检查点只有文件头或名单半写时则返回 `RecoveryRequired`，不会退回旧版本，也不会自动覆盖、清理或重新初始化该目录。

本批没有提供任意半写状态的自动修复、业务操作意图日志或自动重试。它也不能保证外部长期租约存在时仍可无限提交；退休文件占用预算时，普通提交或检查点可以返回 `Limit`。

实现沿用现有 Win7 文件层与 CPU 路径，没有引入 GPU 或特定显卡厂商依赖。Win7 SP1 x64、AMD 真机兼容及断电持久性不由本批 CPU 测试替代。

静态审查记录为 `review.txt` 和 `review-final-static.txt`。审查发现并修正了两处恢复校验缺口：仍存在的前驱必须证明同值且连续的检查点来源；只有当前检查点可以占用维护预留。基础测试为这两项增加了独立反例，避免用其他分叉错误掩盖断言。

首次维护分配测试在 50,442 项处失败，旧接口分配回归在 20,921 项处出现同类失败。两个别名用例都复用了非别名目录的分配次数，而路径长度改变了字符串分配次数。现已分别在同长度目录内校准真实别名调用，并在断言前记录实际注入统计；没有放宽失败输出或私有 CAS 身份的断言。原始失败目录 `maintenance-allocation-full` 和 `old-allocation-full` 保留，修正后的运行另建目录。维护别名实际基准为 172 次，原非别名基准为 174 次。

三个受控错误实现分别为：保留自身退休文件租约、跳过仍存在前驱的同值与连续来源校验、允许普通尾记录借用检查点预留。均以退出码 1 命中指定断言，见 `negative-results.json`。`run_negatives.py` 的 `finally` 恢复原源码字节并重建；恢复后的增强维护专项再次通过 12,722 项。反例未通过修改测试断言制造失败。

分配测试只覆盖健康调用路径校准出的当前线程普通 `new` 和 `new[]` 分配序号，每次注入一个失败。失败路径新增分配、对齐分配、CRT、Win32、CNG 内部分配及多点同时失败不在范围内。测试区分回收准备失败与开始删除后的部分报告，不要求已授权删除能够回滚。

进程专项只在首个退休删除成功后中断，未覆盖每个删除序号。真实子进程退出和成功刷新后重开不等于断电或系统崩溃。检查点刷新 API 报错后的清理成功、清理失败组合尚未在本批新检查点入口完整动态验证；底层文件专项证据不能直接替代该结论。
