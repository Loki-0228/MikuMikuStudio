# PMM 背景图片资产接线与验收

本批在 `codex/plugin-abi` 工作树完成 PMM v1/v2 图片资源入口迁移。目标范围未修改，main 仍为 `6facf91`，阴影同步继续暂缓；未修改 main 或覆盖稳定版程序。

## 已实现的行为

完整配置的 PMM v1/v2 先读取图片路径、位置、比例和显隐，再通过内部 `LoadProjectBackgroundPicture` 准备候选。它与普通换图共用不可变来源捕获、预算和内存解码流程；成功后同时发布纹理、资产及全部图片字段。工程加载保持 clean，保留文件内位置、比例和隐藏状态，不调用普通导入的自动居中计算。

工程中没有图片，或者图片缺失、损坏、超过预算时，清除旧工程的图片、路径、尺寸、位置及资产关联。普通手动换图失败仍保留原图片。非空路径解析失败与工程本来没有图片分别处理：前者只提示一次，后者正常清空。清除把旧 COM 引用交给调用者，在锁外释放；释放期间若新场景接管，不再提示旧场景错误或重复清理。

图片发布后立即准备六个顶点，包括隐藏图片。否则，隐藏图片随后显示时会沿用上一张图的顶点，而显示菜单本身不会重算位置。菜单勾选仍按保存的显隐状态设置。

PMM 加载具有覆盖整个工程的媒体修改作用域，不能使用普通导入的身份获取入口。内部授权额外检查实例、UI 线程、场景代次和图片修改序号：允许工程在图片之前合法加载 AVI；任何更新的图片修改、新建工程或关闭都会阻止旧作用域继续发布。公共身份在加载期间仍不可获取。新授权不放宽一般 `Mutation::Current()` 的判断，也不新增公共 ABI。

原始兼容配置保留原加载分支。本批没有修改 PMM 字节格式、VMD 行为或 MMS 标记规则；旧 C++ `LoadBackgroundPicture` 函数本身也没有整体升级，完整配置的 PMM 已改用新内部入口。

几何检查用 RAII 将宿主原 WRITEONLY 缓冲暂换为同尺寸、FVF、pool 的可读真实 D3D 缓冲，由原生产函数写入，结束后恢复原资源。它验证实际写入几何，不等于读取生产 WRITEONLY 缓冲的兼容性测试、屏幕视觉检查或对 PMM 隐藏图片的真实菜单点击验收。相邻 reset 专项另有菜单 233 重显示检查。

测试在独立目录运行，没有读取用户安装目录设置或替换用户图片。完整配置 PMM 二进制 SHA256 为 `7b91a8f0af96fdbdb80174a6c15d389503b9418d9a1c93574d1628d07e9cca36`；原始配置为 `f83e1797f47669a0226d8b0e81c355469a6d52db68d14bdb71040affff4cb988`。

首次完整配置构建因测试同时包含 `pmm_io_common.hpp` 的手写 VFW 声明和官方 `vfw.h` 失败；测试改为只包含其实际使用的 `pmm_read_buffer.hpp` 后，两配置重建通过。构建证据见 `本地验收记录（未随本文发布）` 和 `*-rebuild.log`。仍有既有共享中间目录及类型比较警告，不计为已修复。两次独立只读审查指出的隐藏图片顶点和缺图反馈缺陷均已修复，针对性检查通过。

USER32 创建窗口成功及本轮隐藏宿主／D3D9 运行，不代表 Win7、AMD、可见界面、真鼠标或多屏验收已经完成。本批身份重入检查的证据包含 CPU 注册表专项与真实 AVI 嵌套加载，不能泛化为整个 PMM 加载器所有模态重入都已验证。

## 下一批：准备后无分配激活与共同历史

后续进度：内部准备与无分配激活已在[同日后续批次](abi-background-picture-activation-2026-10-29.md)实现并验证；实际图片编辑共同历史仍未接线。以下保留本批结束时的设计边界。

PMM 来源待办已完成；背景图片的共同历史仍未完成，操作 1／2 的历史绑定门禁不提前开放。

1. 增加内部 `PreparedPictureActivation`：准备时只保留当前状态并生成候选；从资产字节按已记录解码模式恢复，不能重读原文件或静默改变模式。支持任意摆放、隐藏及空图，不能把没有资产的旧纹理误判为空图。
2. 当前 `Acquire` 使用 unordered_map 插入，不能在历史 Publish 中使用；`Mutation` 构造又会立即使旧身份失效，不能直接用于 Prepare。下一批考虑在已注册 Owner 内增加固定图片票据槽，Prepare 只预留单调编号，Publish 同锁复核后无分配赋值。单纯预留 map node 仍可能在插入时 rehash，不足以保证无分配。
3. Prepare 完成设备引用、解码、费用和身份回执；Publish 仅交换纹理、资产、原生字段及新票据。设备／实例／场景／图片／原字段变化时拒绝旧候选。COM 释放、菜单和绘制刷新在发布及历史提交完成之后执行。
4. 再把图片替换、显隐及摆放统一接入共同历史，按作者选择合并为一次或多次；准备失败和取消不改当前资源、不推进历史，恢复同一资产仍发放新激活票据。完整视频 owner、独立非活动解码状态、真正更换设备时恢复与总体资源费用仍待实现。

以上是下一步设计边界，不是已交付实现，也不缩减全部 ABI 需求。
