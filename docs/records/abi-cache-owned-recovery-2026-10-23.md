# 缓存发布的显式恢复

本批把准备文件、发布意图和 `Store::RecoverOwned` 接入实际 `Initialize`、`InitializeOwned`、`Commit`。存在完整且相互一致的操作记录时，恢复可以确认已完成的提交，或回滚尚未完成的提交。普通读取不执行恢复，不因损坏而退回旧版本。

这是内部缓存元数据协议，没有新增公开插件 ABI，也没有修改 PMM、VMD、VPD 或原快照、提交记录的字节格式。main 已提交 HEAD 核对仍为 `fed9768`。它继续支撑 `3782e0c` 的缓存管理迁移，但真实业务页面、物理额度、工程关联、效果和纹理消费者、管理窗口尚未接入。

## 文件与操作身份

[cache_files.hpp](../../include/mikumikustudio/cache_files.hpp) 增加 `WritePlan` 和可移动的 `PreparedWrite`。`Prepare` 先计算摘要、分配输出，再创建一个独占的零长度文件，返回实际卷与文件身份。`Complete` 在同一句柄写入文件头与负载并刷盘。析构只关闭句柄，不自动删除已经交给调用方的准备文件。

`ReopenPrepared` 校验精确文件身份、长度、单链接和目录保护。`Inspect` 区分未完成文件与完整文件：完整文件必须通过文件头、计划和内容摘要校验。完整但损坏的文件不能被当作半写文件清除。`Flush` 在同一句柄重新校验后执行刷盘；完整可读不等于此前已经刷盘成功。`Abort` 通过同一句柄标记删除，返回删除已接受，不宣称卷空间已回收。

计划中的 owner、名字和预期摘要本身不授予恢复权限。实际恢复还要校验操作记录、前一条提交链、目录锁及所有目标身份。只有尚未尝试写入意图的普通准备失败，发布函数才会用仍持有的创建句柄尝试清理本次准备文件。进程在意图持久化前退出留下的未知文件仍拒绝自动恢复。

[cache_catalog_intent.hpp](../../src/io/cache_catalog_intent.hpp) 定义固定 752 字节、小端、版本 1 的操作记录，标记为 `MMSCacheIntent01`。负载包含非零操作 ID、原 368 字节提交记录、两个各 168 字节的准备计划。编码器检查两个目标同卷且身份不同，快照计划与提交引用一致，提交计划摘要与实际编码内容一致。所有保留字节必须为零。

记录保存于元数据根目录的 `operations`，使用原 128 字节 blob 文件头及新 `CatalogIntent` 类型。key 4 表示发布意图，key 5 表示回滚决定；两者同时存在时，负载必须逐字节相同。最多允许这两条记录，未知文件、重复记录和不一致记录均拒绝恢复。该内部子目录不改变运行数据归入 EXE 同级 `data` 的产品约定。

## 发布与恢复行为

普通发布在持有原目录锁时完成以下顺序：准备快照和提交文件，写入并刷盘意图，完成并刷盘快照，完成并刷盘提交，删除意图，最后发布调用方输出。提交写入开始后的失败返回 `Indeterminate`，输出保持不变。调用方须重新读取并处理恢复要求，不能按错误码盲目重复提交。

存在待处理操作时，普通 `Read`、发布、`Checkpoint` 和 `CollectRetired` 返回 `RecoveryRequired`。显式 `RecoverOwned` 仍取得同一跨进程锁，不绕开既有 CAS。

| 磁盘状态 | 恢复结果 |
| --- | --- |
| 没有操作记录，目录健康 | 校验当前链，返回当前 revision，不写入或删除。 |
| 提交完整，快照完整，没有回滚决定 | 两个已核实句柄分别重新刷盘，再校验完整提交链和最终 head。成功后移除意图，报告 `confirmedPublication`。 |
| 提交尚未完成，旧链与计划一致 | 先写入、刷盘并回读回滚决定，再按精确身份删除计划中的提交和快照，最后移除意图和决定，报告 `rolledBack`。 |
| 已有完整回滚决定 | 重新刷盘该决定并持有读租约，继续同一回滚。只有此时才允许计划目标已经缺失。 |
| 完整提交与回滚决定同时存在 | 拒绝恢复，保留文件。 |
| 意图或决定半写、目标身份替换、完整内容损坏、未知残留 | 拒绝采用或清理，不返回旧链作为成功结果。 |
| 刷盘、删除或读取失败 | 保留调用方报告。已完成的部分回滚可以留下持久决定，下一次调用继续；不承诺磁盘全量回滚。 |

恢复报告只在整个成功分支结束时更新。首次初始化回滚成功后的 revision 为 0；它没有创建一个有效空快照。空库随后仍由初始化入口发布。

容量检查在准备文件之前预留两条操作记录，共 `2 × (128 + 752) = 1760` 字节。普通发布不能借用检查点维护余量。预算专项实际到达 64 MiB 上限减去这份预留的边界，再多一个字节或再提交空快照都会被拒绝，磁盘与输出保持不变。

原始配置记录分别使用 `original-<测试目标名>` 目录。普通分配扫描的计数受运行路径和分配次数影响，不能解释为两套功能数量不同。该扫描没有逐点覆盖 `RecoverOwned` 的分配失败路径。

新增 [cache_catalog_owned_recovery_tests.cpp](../../tests/cache_catalog_owned_recovery_tests.cpp) 对首次指定身份初始化和后续提交分别执行五个真实中断阶段：意图头写入、意图刷盘、快照头写入、提交头写入、提交刷盘。另在回滚决定头写入、决定刷盘、删除提交和删除意图后中断。测试检查实际 API 命中和进程退出码，随后重新打开库验证恢复、拒绝或继续删除的结果。

同一专项还覆盖完整损坏、部分提交配完整损坏快照、身份替换、未知记录、无回滚决定却缺失目标、读租约占用、回滚决定与完整提交矛盾。意图前未知残留由实际准备文件原语构造；没有声称做过发布函数在该窗口的硬退出测试。

六组恢复刷盘故障分别命中快照、提交、既有回滚决定。每个目标都测试调用底层刷盘前返回失败，以及真实刷盘成功后模拟返回失败。失败必须保留报告哨兵、所有文件名字与字节，且没有任何目标删除尝试；解除注入后执行真实恢复、重读和后续提交。夹具此前已成功刷盘，这些测试证明当前恢复正确处理刷盘失败返回值，不证明物理介质在此前失败后的状态。

原 [cache_catalog_recovery_tests.cpp](../../tests/cache_catalog_recovery_tests.cpp) 保留六个原故障场景，并改为显式恢复新协议。删除失败注入已移到实际回滚 `Abort`，检查失败后决定仍在、目标未删，以及重试确实调用成功的删除 API。

`flush-review.txt` 记录了独立代码审查及新增测试审查。增强和原始配置的最终构建分别见 `build-final-full-01.json`、`build-final-original-01.json`。`product-check.json` 确认两产品均为 x64、子系统 6.1，导入与前批最终产品一致，两个效果资源未变，稳定版程序哈希未变。构建没有覆盖稳定版目录。

## 尚未覆盖的范围

本批恢复入口只处理上述普通发布协议。检查点中断仍可能返回 `RecoveryRequired`，不因为新增该入口而变为可自动修复。意图前未知残留、半写意图或决定继续保留文件；没有基于名字、owner 或进程退出猜测删除。

业务 Store、真实页面发布、跨进程物理额度、工程关联、固定、业务清理、效果和纹理消费者及管理窗口仍未完成。后续实现还须把页面与 manifest 的发布、可达集合和清理身份纳入同一业务协议。本批的准备文件原语不代替这些业务约束。

上述测试是受控进程和文件 API 故障，不是断电恢复、Win7 真机或 AMD 真机验收。本批未执行 UI、GPU、第三方 MME 或性能基准测试，不能据此报告提速或完整缓存功能完成。
