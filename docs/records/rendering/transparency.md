## 独立排序程度、跨物体范围与 MotionBlur 兼容

2026-10-21，按用户后续要求，将「显示 → 透明排序」放在同一个二级弹出菜单中，以两条分隔线分为三组，「排序程度」仅作灰色分栏标题，不再包含第三级菜单：

| 菜单 | 行为 |
| --- | --- |
| 关闭 | 默认选中，停止排序 |
| 低、标准、高、最高 | 四个程度直接列出；选择程度会启用排序 |
| 开启跨物体排序 | 独立勾选，默认关闭；关闭排序时可保留该选择 |

四种程度均可选择物体内部或跨物体排序。低使用 16 个深度桶，标准使用 64 个深度桶，高使用 256 个深度桶，三个分桶档位均处理所有三角形，不按数量截断。原生最高档保留深度剥离及 BSP 回退；仅物体内模式按物体独立规划，多物体使用 BSP，单物体仍可深度剥离。

PMM v2 保留原精度字段，增加布尔字段 `org.mikudancestudio.view.transparent_sort_cross_objects`。新建工程与缺少字段的工程默认不跨物体。两个字段独立保存，未知范围值保持原始数据，直到用户主动切换范围。范围变化会使排序计划与 GPU 索引缓存失效，模型和相机未变时仍复用投影结果。下方同日较早的物体内排序记录保留实现过程，其「最高自动跨物体」规则已由本节替代。

用户报告的放射状模糊来自 MotionBlur3+ 的速度图。其 `VelocityMap.fx` 用 `_INDEX` 与 `VERTEXINDEXOFFSET` 读取上一帧顶点位置；原排序路径展开新顶点缓冲，改变了顶点编号。MME 排序现在保留原模型顶点缓冲，只重排原始三角形索引，GPU 继续负责视锥裁剪。为保护同类 MME 的历史数据，MME 最高档使用完整三角形深度排序，不生成切分顶点；它按每个三角形的精确深度稳定排序，比高档的 256 桶更细。此兼容处理不按效果文件名判断，也不修改外部 FX。

下述像素数量来自高档尚未调整为 256 桶时的初次修复验收；降档后的对照结果另存于 `Cache/CompactCacheSort-20261021`。原工程 `Stage.pmm`、`Stage.emm` 内容和修改时间均未改变。关闭、低、高以及四种程度的跨物体模式均成功渲染；修复前关闭与低档有 263,279 个像素不同，修复后同一静止帧的关闭与低档逐像素一致，高档仅有 177 个边缘像素不同。输出为隐藏程序的渲染目标回读，没有抓取用户桌面。

验收还覆盖四档、两种范围的实际 D3D9 像素、范围切换后的缓存失效、PMM 往返保存、三语菜单，以及原版 MME 下所有程度保留原始顶点缓冲。证据位于正式程序目录的 `Cache/MMEPopupTransparencyFix-20261021`。单帧对照用于验证画面，不用于评价帧率。

## 物体内排序与预览内存缓存

2026-10-21，低、标准、高三个档位改为只在各物体内部排序。范围为现有 PMD、PMX 模型透明通道。不同物体保留原有绘制顺序；同一物体内的透明材质仍共同参与排序。

| 档位 | 排序范围与方式 |
| --- | --- |
| 关闭（默认） | 保留原始提交顺序 |
| 低（仅物体内） | 每个物体独立使用 16 个深度桶 |
| 标准（仅物体内） | 每个物体独立使用 64 个深度桶 |
| 高（仅物体内） | 每个物体独立按三角形中心深度稳定排序 |
| 最高 | 保留跨物体逐像素深度剥离及 BSP 回退 |

菜单命令号、工程保存的档位编号与默认关闭不变。跨物体的透明遮挡需要最高档；前三档不会为了修正这种遮挡交换物体顺序。原生几何合批和跨物体回退也不再用于前三档。

### 内存缓存行为

透明排序缓存只存在于当前进程内，不写入磁盘。它保留原始顶点及索引的快照、投影裁剪结果、排序结果、绘制区间，以及私有 GPU 顶点和索引缓冲。

每次渲染核对相机矩阵、参与排序的模型和材质范围，并逐字节比较原始顶点和索引。MME 可以修改原始顶点，因此不能只凭骨骼更新编号判断命中。模型结构与相机未变时，只重新投影顶点或索引发生变化的物体，其他物体复用上次结果。全部投影和排序未变时，也省去 GPU 重新分配及上传。

命中缓存仍执行每个材质的绘制、当前材质参数绑定和 MME 回调。最高档仍逐帧执行深度剥离，不缓存最终画面或减少透明层数。

新增原始数据快照上限为 128 MiB，新增 GPU 缓冲保留上限为 256 MiB。超出上限时按原有逐帧路径处理，不丢弃几何。这两个数不包含原有排序工作向量的内存。设备重置前、应用关闭、关闭排序或透明物体集合清空时释放缓存。`MMS_TRANSPARENT_CACHE_DISABLE=1` 仅供关闭新增缓存做对照。

### 验证记录

CPU 几何回归验证三个档位保持物体顺序、物体内部深度顺序及完整三角形。隐藏 D3D9 像素回归覆盖低、标准、高、最高、关闭、标准档 4× MSAA 和最高档相交透明面，共 7 组，全部通过。缓存验证覆盖 PMD、PMX、固定管线和两种内置效果，包含相机变化、直接写原始顶点、修改索引、材质 alpha 变化，以及一个物体运动而另一个静止。缓存结果均与关闭缓存后重新渲染的像素相同。

静态对照使用 Stage 工程验证副本，两侧均为物体内标准档，11 个模型、741,746 个顶点、8 个附件，RTX 4070 Laptop GPU，实际模型视口 897×504。为消除真实帧间时间对运动模糊及景深的影响，仅在该副本中关闭这两个后处理。原工程及原 EMM 未修改。按关闭、开启、开启、关闭交替运行，每次预热 4 帧、测量 8 帧，未发现后台编译。

| 缓存 | 两次 GPU 排空吞吐率 | 两次中位数 |
| --- | --- | --- |
| 关闭 | 1.059、0.943 帧/秒 | 1.001 帧/秒 |
| 开启 | 9.966、10.015 帧/秒 | 9.990 帧/秒 |

四次输出逐像素一致。该结果是静态编辑器渲染吞吐率，不等于播放或前台窗口 FPS；关闭缓存的两次结果存在约 12% 波动，不据此推算其他工程的增益。记录中的缓存统计覆盖整次进程：开启时 156 次透明准备中有 154 次复用，GPU 上传由 156 次降为 2 次，缓冲分配由 312 次降为 4 次。

原工程保留全部特效的首次静态对照有 227,400 个像素不同，未作为像素一致的验收数据。单独关闭 GPU 缓冲复用后差异仍然存在；隔离运动模糊及景深后消失。原工程的这两个效果读取实际时间，因此原工程快慢两侧的截图不能直接作为确定性像素对照。

实际播放使用未修改的原 PMM 和 EMM，保留全部特效、物理和 Present，每次预热 5 秒、测量 10 秒。两轮完整 ABBA 均在后两次运行检测到其他会话的编译，状态记为 `interference`，不将其 FPS 汇总作为正式性能结果。逐帧记录仍验证所有帧各有 1 次成功 Present、11,510 次绘制和 4,385,200 个三角形，场景时间正常推进，没有靠减少绘制量提速。该 Stage 的采样中投影数据保持静止；运动物体的缓存失效与部分复用由上述像素回归覆盖。

构建、测试、对照日志及图像保存在正式 EXE 根目录的 `Cache/TransparentPreviewValidation-20261021`。构建关闭 PERF 和 DIAG。

## 透明排序三档强度下调

原始记录：`TRANSPARENT_SORT_STRENGTHS_20260927.md`。其中的版本、日期和验证范围沿用原记录。

2026-09-27 按用户要求下调低、标准和高三个档位，最高和关闭保持不变。菜单仍有五档。2026-09-28 按用户要求将默认值改为关闭，已保存工程的明确档位继续生效。

| 档位 | 本次调整后的行为 | 与调整前的关系 |
| --- | --- | --- |
| 关闭（默认） | 按原始提交顺序绘制，不做自动透明排序 | 不变 |
| 低 | 16 个深度桶，远到近，同桶保持输入顺序 | 比原低档的 64 桶更粗 |
| 标准 | 64 个深度桶，远到近，同桶保持输入顺序 | 原低档 |
| 高 | 按完整三角形中心深度稳定排序，同深度按原始序号 | 原标准档 |
| 最高 | 逐像素深度剥离；不支持时回退 BSP | 不变 |

前三个非关闭档位都保留所有有效三角形，不分割几何。桶数减少会降低同桶内的排序精度，不减少绘制的面数。菜单命令号与 PMM 档位字节不变。新建工程和缺少有效档位字段的 PMM 默认关闭排序。已保存的低、标准、高采用新的强度，不迁移成其他档位。

<a id="record-transparent-sort-strengths-最高档保留优化与精度"></a>
### 最高档保留优化与精度

最高档的正常剥离路径按材质提交。剥离上限仍为参与排序的裁剪后三角形数量加一，透明片段耗尽时通过已有遮挡查询提前结束。没有降低层数或增加计数预扫描。

提交 `3b7524a` 的优化继续生效：原生路径排除最终 alpha 为零的材质；剥离不可用时，几何回退结果可以合并屏幕上不重叠的同材质三角形。合批保留重叠区域的原有先后关系。加载 MMEffect 时不启用这两项基于原生语义的优化。BSP 预算仍为额外 4,000,000 个三角形、深度 512、epsilon `2e-13`。

合批的 Rou 性能对照见[透明合批记录](transparency.md#record-transparent-batching)。该测量使用调整前的标准档，对应当前高档，不能作为本次降低排序精度的性能数字。

### 验证范围

- CPU 几何回归通过：16 桶、64 桶、稳定深度排序的区别，以及完整三角形、顶点数据和合批重叠顺序的保留。
- 最高档按修改前、修改后、修改后、修改前交替运行。每侧分别测试普通目标与 4× MSAA，共 8 次运行。所有运行均完成 1,152 层和 4,608 层、alpha 为 `1/255` 的叠加，像素符合独立合成参考。
- 相交透明面、低 alpha 累积及当前高档的 1,152 层完整几何绘制通过，均覆盖普通目标和 4× MSAA。历史参数名 `--peel-budget` 保留，现在验证高档直接排序后的深层绘制。
- 通用 `model_alpha_occlusion_regressions` 的阴影遮罩部分仍有 8 个像素断言失败。修改前后结果相同。该部分引用的 `ZValuePlotAlphaTec`、`ShadowAlphaEnabled` 在当前生产 shader 中不存在，不是本次降档引入，未通过删断言或改期望掩盖。其余透明主体场景和合批的 9,216 像素比较通过。

前后测试均为 VS 2022 x64 Release、同一 Conan toolchain，DIAG/PERF 关闭，隐藏窗口回读。最高档目标为 16×16，使用硬件顶点处理，材质、几何、相机和采样点相同。耗时仅为测试进程时长，不代表播放 FPS。

### 逐项隔离

基线为提交 `51fba13`。前一轮还在 `12f75de` 的不可变发布源码上验证了相同失败：普通遮挡 212 点，四项多层叠加各 9 点。以下步骤依次进行，原有透明主体的颜色期望、容差、几何与采样点保持不变。

| 步骤 | 发现与改动 | 实测结果 |
| --- | --- | --- |
| 纹理查询缓存 | 测试直接追加 `resourcePool`，却没有遵守 `InvalidateTextureLookup()` 契约；第二例纹理无法查询，材质被当作无贴图不透明面绘制。生产 `LoadTextureShared` 已有失效调用。测试改为发布后失效并检查实际绑定，清理时清空条目、失效再释放。 | 低透明度与最大层数的普通/MSAA 共 4 项通过；普通遮挡从 212 点降为 77 点。 |
| 排序档位 | 普通场景默认关闭，却要求两种提交顺序都得到从后到前的叠加。测试显式选择标准档，并增加低、高、最高档注册。 | 四档透明主体均通过，每档只剩阴影实验残留的 8 点。关闭排序仍单独验收。 |
| 阴影契约 | 测试尝试已不存在的 `ZValuePlotAlphaTec` 和 `ShadowAlpha*` 参数，失败后回退到不采样纹理 alpha 的 `ZValuePlotTec`，却仍期待透明孔洞。 | 改为检查当前原生深度技术的真实投影输出，详见下方最终验收。 |

最高档日志在普通与 4× MSAA 两种目标下均记录 256、512、1152、4608 层，全部 `complete=1 committed=1`；4608 层输入为 9216 个三角形。该记录证明完整剥离发生，不能用测试耗时推断播放帧率。

<a id="record-transparent-sort-validation-阴影测试边界"></a>
### 阴影测试边界

按贴图透明度裁剪投影的实验已在[全场景排序实验记录](transparency.md#record-transparency-global-sort)中明确撤回；[五档调整记录](transparency.md#record-transparent-sort-strengths)也已记录这 8 点因生产技术和参数不存在而失败。本次不恢复该实验。

替代用例明确选择当前 `ZValuePlotTec` 并检查调用结果，用两种光源投影矩阵验证 `z/w` 深度。透明、半透明、不透明三个纹理带都必须得到精确的原生深度输出，矩阵平移后深度也必须随之变化。这是当前阴影行为的回归，不宣称实现了透明孔洞投影。

该子场景不经过生产材质级投影筛选，因此不覆盖材质 alpha 的 `0.98f` 门槛。已有 `native_shadow_cycle` 另行覆盖真实帧驱动和 PMX 投影标志；`native_shadow_tests` 检查接收面的阴影采样，两者不能与此处的深度技术测试混称。

<a id="record-transparent-layer-ordering-实现"></a>
### 实现

<a id="record-transparent-layer-ordering-透明检测门控"></a>
#### 透明检测门控

门控分两层，两层都通过才有排序机会。

第一层是材质分类，由 `ModelMaterialUsesAlpha` 决定。满足任一条件即归入透明组：模型的 `postLoadFlag2` 非零；`displayState` 非零；材质 diffuse alpha 小于 1；主纹理含非 255 的 alpha 像素；球面贴图含非 255 的 alpha 像素（PMX 的 `sphereMode` 非零，或非 PMX）。

纹理的 alpha 情况在载入时写入元数据，`model_alpha_pass.hpp` 用 `kTextureAlphaKnown` 表示已检测、`kTextureUsesAlpha` 表示存在非 255 的 alpha 像素。该检测只在载入时扫描一次，之后每帧不再扫描纹理，也不回读 GPU。

第二层是排序门控，在 `RenderNativeOrderedAlpha` 入口。出现以下任一情况时函数直接返回，本轮不做任何排序：已加载 `MMEffect.dll`；线框渲染开启；在内置效果帧中模型处于非显示模式。

单个材质还要额外满足候选条件才参与排序：面顶点数能被 3 整除、三角形数不超过 `kAlphaOrderMaterialTriangles`（4096）、diffuse alpha 为有限正数、`postLoadFlag2` 为零。

<a id="record-transparent-layer-ordering-材质依赖排序"></a>
#### 材质依赖排序

`OrderAlphaMaterials` 只在整个材质层面求解顺序，而且只有当所有重叠三角形对都指向同一结论时才采纳结果。它的输入是一个材质排列 `order`，返回值是 `Unchanged`、`Reordered` 或 `Unsupported`，预算参数默认 262144，诊断信息通过 `AlphaOrderDiagnostic` 输出。

算法分四步。

1. 校验。材质数超过 64、排列长度不匹配、排列有重复或越界时返回 `Unsupported`，原顺序不动。
2. 投影与筛选。所有材质的三角形投影到屏幕空间，坐标必须是有限值且设备深度在 `[0, 1]`，面积为 0 的三角形视为无效数据。三角形按 `minX` 排序并建立 `maxX` 前缀最大值，用区间重叠做粗筛。每一对被检查的三角形都要扣一次预算，即使它随后被边界框判据拒绝，这样长边界框也不会把粗筛变成无上限的平方级工作。
3. 成对深度比较。只有投影后三角形真正相交（凸多边形裁剪出交集多边形，最多 16 个顶点），且相交面积超过两者面积较小值的 `1e-12` 倍，才产生依赖关系。比较用 `epsilon = 1e-7`，这是 float 设备深度的精度量级。如果一对三角形在一个点上 A 在前、在另一个点上 B 在前，说明两者交叉，返回 `Unsupported`，原因是 `crossing`。深度范围完全落在 epsilon 内视为共面，由输入排列的优先级决定先后，从而保留共面时的作者顺序。
4. 拓扑排序。依赖关系记录在边矩阵中，反向边已存在说明依赖互相矛盾，返回 `Unsupported`，原因是 `conflict`。之后每轮按输入排列的优先级选择入度为 0 的材质，若某轮找不到可用材质，说明存在环，返回 `Unsupported`，原因是 `cycle`。

这一层仍然使用精确的交集多边形与深度范围比较，`b7abbc5` 没有改动它。

<a id="record-transparent-layer-ordering-三角形排序与安全合批"></a>
#### 三角形排序与安全合批

只有当材质级排序返回 `Unsupported`，且原因既不是 `invalid` 也不是 `budget` 时，调用方才改用三角形级方案 `BatchAlphaTriangles`。`invalid` 表示数据本身不可用（非有限坐标、深度越界、退化三角形、非法排列），`budget` 表示算力预算耗尽；这两种情况一律不进入三角形回退，整组保留原顺序。

三角形方案先按质心深度从远到近做稳定排序，然后只在屏幕空间不重叠的三角形之间移动顺序，把它们合进更少的绘制段；重叠的三角形保持原有先后。

判断两个三角形是否重叠由 `TrianglesOverlap2D` 完成，`b7abbc5` 用它替换了原来的交集多边形裁剪，只回答“是否重叠”这一个问题，不再算出交集形状。它按双绕序做半平面分离轴判定：依次取两个三角形各自的三条有向边，用该三角形自身面积的符号缩放叉积，因此 PMX 的双面数据两种绕序都成立；只有当另一三角形的三个顶点全部落在同一条边外侧、且超出该边的舍入余量时才判定为分离。余量按 4 个 ULP 与叉积量级计算。触碰、擦边、数值上无法定论的边界情况一律按重叠处理，于是这些情况仍然会产生依赖顺序。

依赖边一律指向初始顺序中更靠后的三角形，因此边不会成环，交叉几何无法构造出环。同一材质内部的三角形也要比较，因为同一材质的两个三角形可能因为纹理而呈现不同颜色。二维 BVH（叶节点阈值为 8）承担粗筛，避免长面部三角形退化成平方级扫描，每次节点访问和每个候选三角形都扣预算。

由此得到的收益是相对逐三角形排序提交而言的：不重叠的三角形被合回同一段。合批可能把同一材质拆成多段，同一材质可以在结果序列中出现多次，每次连续出现对应一次绘制。洛希极限近景原本 6 个透明材质，正是这个方向让它扩成上百个绘制段，段数见验收一节。

限制同样明确：相交三角形的先后仍按质心深度判定，这是近似值；预算耗尽或数据非法时函数返回 `false`，调用方放弃这批排序，整组保留原顺序。

<a id="record-transparent-layer-ordering-保守重叠缓存"></a>
#### 保守重叠缓存

`41a84b0` 加入 `AlphaBatchOverlapCache`，用上一帧算出的候选重叠对复用本帧的粗筛结果，省掉重复的 BVH 遍历与成对判定。

缓存保存三样东西：每个三角形的固定 xy 锚点、每个材质的三角形数量、以及保守的候选对列表。判定能否复用要求这几项同时成立：

- 三角形总数与各材质三角形数量都与缓存一致。数量一变就重建。
- 每个三角形的三个顶点，其 xy 与锚点之差都不超过余量 `padding`（逐顶点验证）。超出余量就重建。
- 缓存的候选对数不超过当前预算。超出即返回 `false`，放弃本次合批。

余量 `padding` 取组内屏幕跨度的 0.002，即 `max(maxX-minX, maxY-minY) * 0.002`。因此缓存只在几何基本静止时命中，移动幅度超过千分之二屏幕跨度就退化为重新求解。

重建时按当前帧的跨度重算余量，并把余量计入保守性，使候选对覆盖三角形在余量范围内任意移动的整个位置范围：包围盒比较允许双方各让出一个 `padding`；分离轴的判据在原有舍入余量上再加 `2 * padding * (abs(dx) + abs(dy))`，其中 `dx`、`dy` 是当前判定边的方向分量。于是只有“整个移动范围都保持分离”的三角形对才被排除，任何在余量内可能重叠的对都留在候选列表里。

命中时锚点不更新。旧候选图覆盖的是重建时算出的那个范围，锚点一旦逐帧移动，判定基准就会超出这张图的覆盖范围，复用结果不再可靠。

深度不参与复用。缓存只保存 xy 锚点和候选对，每次仍然按本帧的 z 把三角形重新做稳定排序，并据此确定依赖边的方向。因此前后关系由本帧深度决定，不会沿用一个已经过期的远近假设。

候选对在复用路径上按当前排序重新映射：先用本帧的稳定排序结果算出每个三角形的名次，再把缓存里的每一对映射成名次对，按远者指向近者的方向建边。这样缓存的候选对只提供“这两者可能重叠”的信息，先后关系仍由本帧深度定向。

保守候选对可能引入额外依赖并增加绘制段。本次近景实测的段数增加，仍受既有预算约束。

<a id="record-transparent-layer-ordering-绘制段数上限"></a>
#### 绘制段数上限

调用方对合批规模设了四道上限，任一超限就丢弃合批结果，恢复该区间的完整原组：

- 单个区间的绘制段数超过 256 时丢弃。
- 整帧被接受的回退组产生的绘制段数之和有硬限 `kAlphaOrderFrameSplitDraws`，值为 512，由提交 `ff2e77b` 加入。它统计的是这些组贡献的全部绘制段，不是相对未合批基线的增量；被拒绝的组不计入。
- 每个区间受 `kAlphaOrderGroupTriangles`（8192）限制，整帧受 `kAlphaOrderFrameTriangles`（16384）限制。
- 整个区间必须由相邻的候选材质组成，非候选材质是排序屏障。

<a id="record-transparent-layer-ordering-缓存与预算"></a>
#### 缓存与预算

排序计划缓存在 `RenderNativeOrderedAlpha` 内，是线程局部的。它保存上一批的几何、材质排列、三角形引用、诊断信息和结果，判定是否复用的方式是把本帧投影出的三角形与缓存逐字节比较。几何没变就跳过整个求解过程，直接复用上次的排列或合批结果；几何变了就重新求解并覆盖缓存。追踪日志中的 `cached=1` 与 `cached=0` 就是这一比较的结果。缓存与线程绑定，不跨帧保留 D3D 资源。

另有 `AlphaBatchOverlapCache` 负责候选重叠对，作用范围与失效条件见上一节。

| 预算 | 默认值 | 触顶行为 |
| --- | --- | --- |
| 材质数上限 | 64 | 返回 `Unsupported`，原因 `invalid`，不进入三角形回退 |
| 成对比较预算 | 262144 | 返回 `Unsupported`，原因 `budget`，不进入三角形回退 |
| 三角形排序预算 | 262144 | 返回 `false`，放弃合批，整组保留原顺序 |
| 材质三角形数 | 4096 | 该材质不作为候选 |
| 区间三角形数 | 8192 | 该区间不参与排序 |
| 整帧三角形数 | 16384 | 该区间不参与排序 |
| 整帧回退段数之和 | 512 | 该区间丢弃合批结果 |
| 单区间绘制段数 | 256 | 该区间丢弃合批结果 |

<a id="record-transparent-layer-ordering-mme-边界"></a>
#### MME 边界

检测到 `MMEffect.dll` 时，本方案整体旁路：`RenderNativeOrderedAlpha` 在入口直接返回，不排序、不读顶点缓冲、不改变任何提交顺序，渲染完全走原有路径，原生路径上的排序结果因此不能推广到第三方 MME 效果。没有 MME 时，材质内三角形排序的时机提前到不透明阶段之前，避免修改已经提交的索引缓冲。

<a id="record-transparent-layer-ordering-限制"></a>
### 限制

- 材质级排序遇到交叉、矛盾或环时放弃；放弃后改用三角形级方案，但其中相交三角形仍按质心深度近似。
- 超限回退意味着回到本次修复前的提交次序，原有的透明遮挡问题可能在该区间继续存在，规模被限制在受控范围内。
- 保守重叠缓存可能增加绘制段；本次近景实测的段数增加。交付版对相同几何的连续帧只做一次无 `padding` 合批，静止画面的后续帧因此回到 103 段。移动近景按完整 150 帧 TRACE，绘制段落在 179 至 234 之间，拒绝次数为 0，未触及 256 段的单区间上限；更早的固定近景 179 段与移动近景 65 帧 195 至 233 段是短程采样，只作历史记录。
- 排序区间必须是相邻的候选材质连续段，超出范围的几何保持原有提交顺序，跨模型与跨区间的遮挡关系不作保证。
- 近远裁剪面之外的几何不参与求解。一个区间只要跨出任一裁剪面，就无法使用这套未裁剪的判定，整组放弃。
- 合批的段数少于逐三角形排序提交，但可能远多于透明材质数，例如洛希极限近景的 6 个材质对应上百段。
- 用户报告的原截图问题未能完全复现与确认，详见验收一节的复现状态。

<a id="record-transparency-occlusion-问题与兼容范围"></a>
### 问题与兼容范围

前方半透明像素应与后方可见表面混合。如果前方像素先写入深度，后方表面又尚未绘制，后方表面会被深度测试拒绝，前方像素便与清屏背景混合。白色背景下，这可能表现为白边。

已有实现先画不透明材质，再画透明材质，并在每个透明材质内排序三角形。但纹理只要有一个非不透明像素，整个材质都会归入透明组；同一纹理中的实心像素也因此延后。仅有材质分组不能保证这些像素在混合前已经进入颜色缓冲。

本次修复以像素遮挡关系为验收依据，原版 MMD 用作行为和帧率参照。用户素材不作修改。

增强作用于原生 D3D9 固定管线和内置自阴影渲染。实验性的 D3D12 预览不在本次实现范围内。MME 可替换材质着色器、绘制次数和深度状态；检测到 `MMEffect.dll` 时保留原有提交行为，不能把原生验证结果推广到第三方 MME 效果。

<a id="record-transparency-occlusion-实现"></a>
### 实现

原生不透明阶段提前绘制含 alpha 纹理材质中的实心覆盖部分：临时把 `ALPHAREF` 设为 255，沿用 `GREATEREQUAL`。后续透明阶段仍按原路径绘制平滑边缘，并保留描边依赖的深度写入。固定管线绘制后恢复调用前的参考值；内置效果在 `FxBeginPass` 安装状态块之后设置参考值，在 `FxEndPass` 前恢复。

只有材质 diffuse alpha 不低于 1、未处于模型半透明显示/淡出状态、且非阴影专用绘制时才增加这次提交。原生三角形排序提前到不透明阶段之前，避免修改已经提交的索引缓冲；MME 排序时机保持原样。

纹理透明分类继续使用载入时的元数据，不增加每帧纹理扫描或 GPU 回读。完全不透明材质没有额外绘制。含 alpha 的材质可能增加一次材质绘制及实心区域填充，实测成本另列。

这不是通用透明排序算法。它确保混合前已有 alpha 纹理的实心遮挡信息；两个真正半透明表面的跨模型交错、相交和循环遮挡仍受提交顺序影响。只含部分透明像素而没有实心覆盖的后方表面不在保证范围内。

<a id="record-transparency-occlusion-面部半透明叠层的补充分析"></a>
### 面部半透明叠层的补充分析

用户补充了面部近景，报告半透明层穿过其他表面。本节仅根据代码和素材只读检查分析，没有在用户停止测试后启动渲染，也没有确认该截图使用的 build、显示模式或 MME 状态。

当前 `SortTransparentModelMaterials` 逐个材质范围调用三角形排序；`DrawModelMaterials` 仍按 PMX 材质索引提交，模型之间仍按用户顺序。因而材质内部排序并未解决不同透明材质之间的混合顺序。

只读检查 `tests/洛希极限/洛天依洛希极限_横向关节改名.pmx` 得到以下结果，序号从 0 开始：

| 材质 | 序号 | 主纹理 alpha 情况 |
| --- | --- | --- |
| `00_Face`、`00_Face.001` | 1、10 | `_041212.png` 全部为 255 |
| `00_FaceBrow`、`00_FaceEyeline`、`00_FaceEyelash` | 2、3、4 | 均包含真正半透明像素 |
| `00_EyeWhite`、`00_EyeIris`、`00_EyeHighlight` | 5、6、7 | 均包含部分透明像素 |
| `000_Hair_01`、`000_Hair_01.001` | 14、15 | `hair_basecolor.png` 同时包含透明、半透明和实心像素 |

这些材质的基础 diffuse alpha 均为 1。也就是说，面部底色本身并非半透明，眉眼叠层和头发软边才需要透明混合；脸部材质原本就早于头发。上述统计是原始纹理层面的检查，不能推断截图中采样、材质变形或效果着色后的实际 alpha。

透明混合只把当前颜色与已绘制颜色相混合，深度缓冲仍只保存一个深度值。前面的半透明层过早写深度，可能挡掉之后提交的后层；后层若没有正确深度测试，也可能盖到前景上。这是不同故障路径，截图不足以确定具体状态。Direct3D 分别控制混合、深度测试和深度写入，见 [颜色混合公式](https://learn.microsoft.com/en-us/windows/win32/direct3d9/alpha-texture-blending) 与 [深度和 alpha 渲染状态](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3drenderstatetype)。

对稳定贴附于脸部的叠层，按底层到表层调整材质提交顺序可能缓解问题，例如先画面部和眼球底层，再画眉眼透明叠层；无需独立形变的妆容也可合入不透明面部纹理。相交、动画改变前后关系或跨模型重叠时，单一材质顺序无法保证正确。原模型已经将面部放在头发前面，不能把相同重排当作已确认修复。

若在相同相机、姿态、显示模式和效果下，原版 MMD 正常而本项目异常，应作为渲染兼容问题修复。现有实心像素提前绘制只覆盖部分情况，不宣称已解决全部面部透明层问题。后续先定位出错的具体绘制与深度状态，再比较前后 build 的后台画面和性能；不直接全局关闭深度写入，以免破坏透明材质与描边的遮挡。

### 验收方法

- 直接调用生产模型渲染函数，用真实 D3D9 设备回读像素。前方黑色半透明纹理与后方蓝色实心纹理重叠；后方纹理在别处含透明像素，使其同样进入透明材质组。

### 独立基准测量约定

使用同一台机器、同一 GPU、VS 2022 x64 Release 与 `/O2 /Ob2 /DNDEBUG`。正式对照关闭 `MIKUDANCESTUDIO_PERF` 和 `MIKUDANCESTUDIO_DIAG`；阶段分析另外构建，不能与正式样本混算。

主要指标是包含末尾 GPU 排空的整批耗时除以帧数，其倒数是批次吞吐率，不是窗口 FPS。逐帧耗时的 P95 在 throughput 模式下包含 CPU 提交和阻塞，不能当作 GPU 单帧时延。保留原始 JSON、日志、版本和可执行文件哈希；无法测得的 draw 数量不填写估计值。

HGrass 没有物理刚体，因此它只能验证多模型渲染负载，不能证明角色物理性能有所改善。任何优化不得依靠关闭物理、透明排序、描边或降低模型质量获得收益。

### 后续更新：透明层排序

上文记录的实心 alpha 预通道修复及其测试证据保持不变，仍按原文描述的范围成立。

新增的透明层排序实现单独记录在 [透明层排序：实现、限制与验收](transparency.md#record-transparent-layer-ordering)。该实现的生产修复提交为 `60595e1`，代码基线为 `34a958b`；该文档写明检测门控、材质级求解、三角形排序与合批、预算表、MME 边界，以及已核验的验收结果。

当前实现能力如下。排序在设定了预算上限的前提下，支持连续的候选材质组跨材质、跨模型求解顺序。材质级求解只有因交叉（`crossing`）、依赖矛盾（`conflict`）或环（`cycle`）失败时才改试三角形级方案，按三角形质心深度排序，并在重叠约束下做合批；因数据非法（`invalid`）或预算耗尽（`budget`）失败时不回退，整组保留原顺序。

当前实现的限制如下。大材质、近远裁剪面、运行时预算和 MME 都仍然构成限制，超出范围或触发上限的几何保持原有提交顺序。该实现不是顺序无关的逐像素精确 OIT，用户报告的原截图问题也尚未取得同条件的截图对照证据。因此上文中有关尚未支持透明材质间排序的历史描述，是那次修复当时的状态记录，不能当作当前结论。

性能结论同样尚未验收，本文与上述排序文档都不填写估计值。本节不新增性能数据，也不改动上文的验证记录。

<a id="record-transparent-sort-limit-pmm-最高上限的工作量"></a>
### 最高上限的工作量

标准、高、极高保持 1024、2048、4096 次分层迭代上限。最高采用当前参与排序、裁剪后的三角形数量加一：单个三角形在一个像素最多贡献一层，多出的一次用于空查询确认完成。沿用每层已有的遮挡查询，片段耗尽即结束，没有独立计数预扫描。

这个值是安全上界，不是预先算出的最小层数。当前云镜头包含 21,412 个参与排序的三角形，最高上界 21,413，实际 668 层就完成。分层须完整完成后才提交；遇到设备/效果错误则丢弃私有中间结果，并回退完整几何。

最高只在支持的内置 SM3 分层路径上动态推进。自定义 MME shader、SM2、固定管线或资源不足时，BSP 回退使用现有极高预算（额外 400 万三角形、深度 512、epsilon 2e-13），仍可能近似排序。配件 `.x` 的独立通道和 MSAA 部分覆盖的限制沿用 [浮点合成记录](transparency.md#record-cloud-float-compositing)，不能据此声称所有效果都已精确排序。

测试使用 1152 层与 4608 层的 alpha=1/255 黑色面，白底参考值分别约 2.76 和 0.00，RGB 容差 2，目标 A 必须为 255。同一测试源码在两个生产核心上分别构建，并测试单采样和 4x MSAA。初次驱动继承了原测试的 `D3DCREATE_SOFTWARE_VERTEXPROCESSING`，与生产云测评的硬件顶点处理不同。旧版两种采样模式均得到白色 (255,255,255)，各有 18 个失败样本，trace 在 1024 层回退。新版单采样先触发 180 秒超时，延长后通过：1152 层为 (3,3,3)，4608 层为 (0,0,0)，A 均为 255，实际完成 1152/4608 层；整组用时约 443 秒。软件顶点处理的 4x MSAA 组在 600 秒超时，1152 层通过，4608 层未完成。这些长耗时不能当作生产版性能。

随后把最高模式改为与生产相同的硬件顶点处理，并打印、断言实际设备标志为 `0x40`。96×96 的旧版硬件两组仍各有 18 个错误采样点；新版全尺寸硬件运行由协调者提前停止，保留为未验收诊断，不将未完成结果写成通过。

常规层数边界测试随后改为 16×16 目标，前后两侧同步相同驱动，仍保留全部 1152/4608 层、原 shader、alpha、九个采样点和完整解析式断言。只减少重复填充面积，不减少层数或几何，不用于生产性能比较。`--maximum-full-size` 仍可运行原 96×96 压力用例，支持附加 `--msaa`。真实云图的 1076×606 视口及性能采样从未缩小。硬件全尺寸诊断见 `hardware-checks/`，常规有界测试结果见 `compact-checks/`，软件路径与超时证据仍保留在 `checks/`。

最终 16×16 硬件路径对照结果如下，四组使用相同驱动源码和设备标志：

| 模式 | 修复前 | 修复后 |
| --- | --- | --- |
| 单采样 | 1152/4608 层均输出 255，18 个采样失败 | 分别输出 3 / 0，全部 RGB 与 A255 检查通过 |
| 4x MSAA | 1152/4608 层均输出 255，18 个采样失败 | 分别输出 3 / 0，全部 RGB 与 A255 检查通过 |

新版 trace 分别记录 `layers=1152/4608 complete=1 committed=1`；旧版均在 1024 层未完成并回退。新版两组完整进程约 11.4 / 11.1 秒，旧版约 3.6 / 3.5 秒；这些是专用正确性用例的总耗时，旧版没有完成相同透明工作，不能据此评估生产 FPS 或声称等画质加速。软件路径 96×96 单采样的通过作为额外证据保留，96×96 MSAA 超时仍标记为未验收。

<a id="record-cloud-float-compositing-结论与边界"></a>
### 结论与边界

已修复两个独立缺陷：透明层逐层写回 8 位目标导致低 alpha 贡献因舍入而丢失；同一混合因子错误地作用于目标 alpha，导致已经合成天空的云图再次带透明度。Toon 调整不能修复这两项。另修复分层预算耗尽时只留下远层、漏掉最近层的问题。

当前 `cloud.pmm` 的天空来自 `UserFile/Model/Sky/Blue.bmp` 背景图片。工程加载一个 ToonCloud PMX 和一个 ikParticle 配件，ToonCloud 贴图表只有 `cloud.tga`、`CToon.png`，没有单独的天空球几何。背景图片经 `DrawPreModelQuads` 在模型前绘制、关闭深度测试，不加入透明三角形集合。不能将本场景的问题表述成天空球三角形排序失败；其他真正的天空球或自定义效果需独立验证。

<a id="record-cloud-float-compositing-为什么调白-toon-后图片仍会发黑"></a>
### 为什么调白 Toon 后图片仍会发黑

旧混合把 RGB 与 alpha 都用 `SRCALPHA / INVSRCALPHA`：

- RGB：`Cs * As + Cd * (1-As)`。
- 错误的目标 alpha：`As * As + Ad * (1-As)`。
- 正确的目标 alpha：`As + Ad * (1-As)`。

当目标原本已是不透明天空（Ad=1），正确结果仍应为1。旧式会把目标 alpha 压低。导出的 PNG 把已经含天空的 RGB 和错误 alpha 一起保存；在深色底上再次显示时就会发暗。窗口内 RGB 与导出 PNG 的再次合成不能混作一个证据。

修复前纯白 Toon 控制图中，云内部 RGB 三通道均至少250的117990像素，alpha范围42–178，中位85；对应原 Toon 的 alpha 分布相同。改变 Toon 只改变色值，未修正该错误。

<a id="record-cloud-float-compositing-实现"></a>
### 实现

保留原片段选层、同深度稳定编号、原材质与光照输出。使用两组私有 FP32 颜色/最近深度目标，每层先复制前一组，再在 shader 中手算预乘颜色与累计 alpha；未完成时原颜色和深度保持不变。全部分层完成才以 `ONE / INVSRCALPHA` 一次提交并恢复最近有效深度。未完成或出错则重新走完整几何回退，不保留半份结果。

最初尝试直接对 FP32 目标做硬件混合，RTX4070 Laptop 的 D3D9 能力查询不支持，实际发生回退。最终实现不依赖该能力。

普通深度直接用于只读遮挡测试。MSAA 深度不能与单采样 FP32 目标混绑，因此每层先在同采样类型、同质量级别的 FP16 掩码目标上按原深度测试，再 resolve 为覆盖率；源颜色与累计结果仍为 FP32。设备不支持所需资源或 resolve 失败时完整回退，不关闭抗锯齿或遮挡测试。

MSAA 掩码保留像素覆盖比例，仍不是每个子采样独立保存完整透明链。部分遮挡边界、任意自定义 shader、配件 `.x` 与模型的统一全局排序不在本轮准确性证明内。标准/高/极高层上限仍为1024/2048/4096，菜单及 PMM v2 精度字段未改；标准档还不能视作已完成性能验收的最终默认值。

### 当前逐像素分层原型

对匹配内置 SM3 着色器的 MME 材质，候选在每个像素从远到近剥离透明片段，再按原颜色和 alpha 混合。深度使用 24 位整数键，同深度按稳定三角形编号推进。零 alpha 片段不参与。每层使用遮挡查询判断是否还有片段，不依赖三角形中心顺序。

原型先通过原 MME 回调预检实际 shader 字节码，只接受六种内置 SM3 技术；自定义 shader、SM2、固定管线、无法创建目标等情况保留 BSP 路径。内部清屏和合成临时清除 MME 当前对象上下文，避免被当成模型绘制；材质本身继续使用原回调、光照、贴图和自阴影参数。

<a id="record-cloud-transparency-experiment-已确认原因"></a>
### 已确认原因

素材为 `D:/MMD-Next/tests/ToonGlass_Ray/UserFile/cloud.pmm`。云模型包含 95,400 个顶点、31,800 个三角形、15 个材质；材质使用同一张带连续 Alpha 的 `cloud.tga`。

MME 还有一个独立限制：`RenderNativeOrderedAlpha` 只要发现 `MMEffect.dll` 已加载就提前返回。即使云模型没有自定义效果，原生跨材质排序也不会执行。

<a id="record-cloud-transparency-experiment-候选行为及限制"></a>
### 候选行为及限制

原生路径检查连续材质的完整渲染属性、贴图和 PMX 实时材质 Morph 通道是否一致。大于原有组上限的等价材质使用一个临时索引流整体排序。CPU 原始索引不变，描边和阴影仍使用原材质范围。这是同模型内等价材质的优化，不代表任意跨模型透明问题已经解决。

<a id="record-transparency-global-sort-排序容量与跨模型"></a>
### 排序容量与跨模型

排序容量按实际索引中的三角形数增长，而不是用总顶点数作为三角形上限。共享顶点会让三角形数超过顶点数，这个模型就是实例。正常透明材质进入跨模型的同一队列，完全不可见的材质不再切断队列。

先尝试材质级排序。材质相互穿插、数量超过材质求解器范围或比较预算不足时，改用全组的稳定三角形深度排序。合批只能移动在屏幕上不重叠的三角形。小组用三角形重叠图合批，同材质的内部次序用相邻链保存。超过 4096 个可见三角形或图求解预算不足时，用屏幕网格合批：每个单元格保存各材质尚未绘制的最早深度名次，只有不会越过更远重叠几何时才继续当前材质。网格从 32×32 开始，成员引用过多时合并单元格；粗网格只增加依赖，不丢掉遮挡关系。4096 是算法切换点，不再是排序容量上限。

材质级比较先排除屏幕包围盒不相交的材质对，只在不同材质之间搜索三角形交集。深度区间完全分离的材质对在找到一个真实交集后即可确定先后关系，单纯包围盒重叠不会强制交换。

合批预算不足时保留深度次序，不再恢复错误的原始材质次序。视锥外三角形排除；跨近远裁剪面的三角形以可见裁剪多边形的保守包围范围参与。

纹理覆盖查询另有保守筛选：128×128 以内的分块积分表只排除 UV 范围内连同过滤边界都完全不透明的三角形。它仅用于常规 PMX、双线性采样、没有额外 alpha 影响的材质；各向异性过滤、附加 UV 球贴、显示透明和不确定情况均保留全部几何。本机默认各向异性采样，因此不能把离线估算的透明三角形数量写成运行时收益。缓存只读托管 A8R8G8B8 纹理，容量为 64 项。

相交三角形仍按投影深度质心近似。这不能解决需要切分几何的循环遮挡，也不是逐像素精确 OIT。MME、线框和特殊显示模式仍沿用原路径；加法材质保留顺序屏障。

<a id="record-transparency-global-sort-面部画面与阴影"></a>
### 面部画面与阴影

早期近景没有真正进入内置自阴影渲染器。仅设置 `SelfShadowMode` 不足以启动它；驱动现在同时设置视口编辑模式和 `selfShadowEnabled`，并在 JSON 中记录 `effect_model_renderer` 的实际值。阴影关闭和模式 1/2 分别验证为 false、true、true。

在实际阴影路径中复现了截图中的脸颊粉白斑块。诊断副本只清除头发的自阴影投射标志后，斑块消失；调整眼线/面部材质次序并不消除它。原 PMX 保持不变。这个实验把斑块定位到头发投射的阴影，只是一条诊断事实：它既不能证明每一块阴影都是错误，也不能作为判定面部透明故障的依据。

原 `ZValuePlotTec` 不读取主贴图 alpha。新增的原生阴影技术裁掉 `diffuse alpha × 主贴图 alpha < 1/255` 的像素，并保留有实体覆盖的投影。SM2/SM3 和预生成 `.res` 同步更新。该遮罩解决透明孔洞投影，不提供连续的半透明阴影透射。遮罩后粉白斑块仍可复现，但这只说明斑块随头发阴影变化，不能据此断言面部透明故障未修复，也不能据此宣称面部已全部修复。

只改变阴影双面剔除的诊断也没有消除白斑。`000_Hair_01` 的 flags 为 0x0F，主画面与原阴影通道对双面的解释确实不同，但这个差异不能据实测认定为白斑根因，该实验没有进入交付源码。粉白斑块与眼影/睫毛穿过刘海是不同现象。单凭粉白斑块的存在或消失，不能判定面部透明故障是否修复。若要单独判断斑块本身是否正确，应与原版 MMD 在同条件下比较渲染结果。没有靠关闭头发投影来宣称修复。
