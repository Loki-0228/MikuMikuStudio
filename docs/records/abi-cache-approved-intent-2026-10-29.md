# 来源写入的持久批准凭据

本批将来源元数据准入的实际审批结果写入 catalog 操作日志，在真实候选文件身份已固定、正文尚未写入的位置保存凭据。普通旧日志不会自动获得批准资格。目标不变；这是统一恢复执行器的前置实现，尚未完成其接线、Checkpoint 许可或视频生产迁移。

## 实际接线

`SourceAdmission::Commit` 改用 `PlanApprovedCommit` 和 `ExecuteApproved`。管理器沿已固定根实际读取 Manager、Video、Control、Catalog、Pages、Raw、Snapshots、Commits、Operations 九处目录身份；从同次完整盘点、现有预留、来源投影和刚重读的设置形成 `PublicationApproval`。

凭据记录分配单位、物理占用、旧 writer 剩余预留、变更前后 raw 残额／元数据责任、当时的限额及启用状态、批准峰值。编解码重新验证以下计算，任何加法或逐文件取整溢出均拒绝：

```
峰值 = 物理占用 + 旧预留 + 变更后 raw 残额 + 变更后元数据责任
     + 本次四个文件分别取整后的大小
基线 = 物理占用 + 旧预留 + 变更前 raw 残额 + 变更前元数据责任
批准条件 = 峰值不超过基线，或缓存启用且峰值不超过当时限额
```

这仍是同一管理器总账，不是第二份独立额度。构造或解码一个结构体本身不授予权限：catalog 依赖可信管理器提供真实账目；其自身只校验格式、计算和实际内部目录身份。未来统一恢复入口仍须核对全部外侧目录、真实当前残留和来源责任。

批准计划不创建缺失的锁或 operations 目录。执行必须先通过纯审批检查、已有目录和版本检查；普通 `Execute` 不能绕过批准入口。随后固定实际零长 snapshot／commit 计划，写入并验证完整批准日志，才允许写候选正文。成功提交后删除该日志；失败留下可验证日志时，恢复计划提供 `RecoveryApproval()`，不会重放一个新的 Commit。

## 格式及回滚

新日志 payload 为 1008 字节，加封套后每份 1136 字节；单独按实际分配单位计费。普通 intent 的 752 字节 payload、旧 Key 和编解码保持原状。

| 偏移 | 内容 |
| --- | --- |
| 0–31 | 独立 `MMSCacheApprv001` magic、版本及零保留字段 |
| 32–783 | 原有 752 字节精确事务记录，包含真实候选计划和前置版本 |
| 784–927 | 九处物理目录身份，按固定顺序各 16 字节 |
| 928–999 | 九个 64 位计费字段 |
| 1000–1007 | 策略启用标志及零保留字段 |

批准 intent 使用独立 Key 6，批准 rollback decision 使用 Key 7；普通 Key 4／5 不赋予许可。两份日志存在时必须完全同格式、同批准内容和同事务字节；未知 key、混合格式、保留位异常、截断或矛盾信息均拒绝。回滚 decision 保留同一完整批准内容，避免 intent 删除后丢失证据。

`ApprovedPublicationFootprint` 供实际发布和后续来源责任共用，包含较大的批准 intent 与 rollback decision。恢复按实际日志长度计费，不能继续套普通日志的较小值。目录同卷、两两不同，候选文件不能与任何目录身份重合；卷序列号 0 不被错误当作无效值。

## 仍未完成

批准凭据已经实际写入和跨进程读回，但统一管理器尚未开放消费它的恢复会话。下一步应拆出公共锁和状态固定阶段，贯穿真实盘点、全部身份／责任复核和执行原恢复计划；不能因日志称“已批准”便跳过当前残留核算，也不能为无可信凭据的普通日志默认兑现旧许可。

Checkpoint 的当前协议没有同样的 intent，许可和失败恢复须另行完成。可信初始化、raw 捕获各阶段、视频激活、帧租约和共同历史继续待办。半写且失去可信计划的残留保守按 unknown 处理，不能凭名称删除；逻辑批准不等于物理磁盘空间已保留，没有新增断电、磁盘写满、Win7／AMD 真机或真实鼠标通过声明。
