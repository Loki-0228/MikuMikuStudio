# HIS-01：跨零粘贴准备边界

本次不扩大 421 或 422 的生产行为。完整档现有负帧专用 421 继续使用 420 的不可变复制回执；实际跨零成功仍待实现。新增 421 回归使用真实 420 复制同一镜头或表情轨道上的负帧与正帧，在两种历史模式分别尝试把原生键放到 0 和 1。用例要求整批拒绝，保留两边的键、零帧锚点、姿态、选择、两个模式的复制回执、场景修订和已有重做。

## 尚缺的事务接口

- 420 回执用 `first` 保存带符号的共同起点，`nativeFirst` 保存原生起点。原生行的真实偏移是 `nativeFirst - first + nativeRelativeFrame`。先以有符号 64 位计算，再按目标帧分区；0 属于原生键池。一行落到负数不代表同一批的下一行也落到负数。
- `PlanGlobalKeyPaste` 和 `PlanModelKeyPaste` 即使收到独立、已经重算偏移的载荷，也拒绝负播放头；全局候选的 `PrepareWithIntent` 在撤销重做时同样拒绝。不能通过暂移播放头规避这些条件，准备过程需要按实际帧保留姿态和游标。
- 负帧插值可能依赖原生第 0 帧。现有跨零删除先准备原生候选并向负帧候选提供目标零帧、显示/IK 和父绑定信息，再统一验证和发布。粘贴候选没有等价接口。顺序提交两个历史记录会留下部分成功，独立准备两个候选则会用旧零帧求负帧姿态。
- 旧的混合负帧适配器不是无损转换：它读取可变的旁路剪贴板，重建负帧行时没有保留相机插值或模型选择器等原生字段。本次没有把这条路径接到新的跨零分支。

下一步是给独立原生粘贴计划增加实际负播放头下的准备和回放能力，提供正向与撤销方向的目标零帧和关联所有权，补齐两种目标存储之间的完整载荷转换。完成后，按跨零删除已有模式将双方置于一个有界历史候选，先检查全部写入条件，再一次发布，最后才更新 UI。用真实命令确认单步提交、单步撤销重做、零帧插值、分配失败和复制后模型更换，再替换暂时的整批拒绝断言。

## 验证范围

Linux CPU 专项以 GCC `-O2` 及 `-fsanitize=address,undefined` 各通过 451 项，含本次新增的原生相对偏移、跨到 0／1 及无符号辅助函数拒绝负起点。沙箱不支持 LeakSanitizer，因此关闭泄漏检查；此结果不覆盖内存泄漏或 420／421。Windows 需在完整档开启 `MIKUMIKUSTUDIO_BUILD_UI_TESTS`，显式构建 `native_edit_history_tests`，在隔离的 Windows 环境运行 `--signed-paste-command-only`；云环境没有 Windows 工具链和运行时，命令级用例在此未编译或运行。
